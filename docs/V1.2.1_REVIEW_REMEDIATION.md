## 2. 逐项整改明细

### P0-2 生产/多进程模式强制 PostgreSQL

**问题**：`.env.example` 与 `config.py` 默认 SQLite，而常驻部署会启动 API、Market Worker、Execution Worker、Recovery Watchdog 多个 OS 进程；`outbox/service.py` 在非 PostgreSQL 方言下退化为进程内 `threading.Lock`，无法跨进程保证认领唯一性。

**修改文件**

| 文件 | 改动 |
|---|---|
| `services/api/app/core/db_policy.py`（新增） | `dialect_of()` / `redact_url()` / `assert_trading_runtime_database()` / `worker_role_requires_postgres()`；方言不合规抛 `DatabasePolicyError` |
| `services/api/app/core/config.py` | 新增 `REQUIRE_DB_DIALECT`、`ENFORCE_DB_DIALECT_IN_PRODUCTION`、`DB_POLICY_ALLOW_SQLITE_IN_PRODUCTION` |
| `services/api/app/db/bootstrap.py` | `alembic upgrade head` 后校验"已应用 revision == 唯一 head"，不一致抛错；记录 `last_bootstrap_report` |
| `services/api/app/workers/runner.py` | 启动前调用策略检查；新增 `--allow-unsafe-sqlite` 显式逃生口（打印 `NOT SAFE FOR MULTI-PROCESS` 警告）；违规退出码 2 |
| `.env.example`、`docs/RUNBOOK.md`、`README.md` | 生产必须 PostgreSQL；补充 `initdb` / `createuser` / `createdb` / `alembic upgrade head` 步骤 |

**测试**：`services/api/tests/test_db_policy.py`（9 项）

**验收结果**

```
python -m pytest tests/test_db_policy.py -q                 -> 9 passed
python -m pytest tests/test_db_policy.py tests/test_postgres_dialect.py tests/test_core_and_schemas.py -q
                                                            -> 23 passed
```

拒绝时的实际错误文本：

```
Multi-process worker role 'execution-worker' is not permitted to run on database dialect 'sqlite'.
SQLite does not provide cross-process transactional outbox locking (FOR UPDATE SKIP LOCKED) and
is NOT SAFE FOR MULTI-PROCESS execution. Remediation: (1) Set DATABASE_URL to a
postgresql+psycopg:// connection string, (2) run 'alembic upgrade head', or
(3) pass --allow-unsafe-sqlite for local single-process experiments.
```

**未覆盖边界**：真正启动 4 个 launchd 进程连同一个 PostgreSQL 的验收仍需在 Mac mini 上执行；本轮只验证了策略判定与 runner 退出码。

## 4. 仍未修复（下一轮必须处理）

| 编号 | 条目 | 为什么本轮没做 | 影响 |
|---|---|---|---|
| **P0-1** | Binance / OKX 仍是模拟适配器 | 需要真实 Testnet/Demo 凭证与远端联调，无法在本机离线完成 | **系统不能用于实盘**；一切"连接成功/成交/保护单"均为模拟 |
| **P1-1** | 外部下单与数据库提交之间的双写窗口 | 需要重构 `execution/engine.py` 的下单事务边界（先持久化 `SUBMITTING` 意图，重放前按 client ID 查询交易所） | 崩溃可能造成"远端已成交、本地无记录"，重放后重复下单 |
| **P1-2** | 订单响应映射过于乐观（缺 `exchange_order_id` 时造 ID、缺 `tp_sl_confirmed` 时默认 True、未知状态归为 FILLED） | 与 P1-1 同一文件同一事务边界，合并做更安全 | 真实交易所响应会被误判为成功 |
| **P1-6** | 外部心跳 `send_heartbeat()` 无调度调用者 | 需要外部监控服务 | Mac 整机离线无告警 |
| **P1-7** | 备份恢复检查未恢复到隔离 PostgreSQL | 需要 CI 级临时数据库编排 | 备份"可解密"≠"可恢复" |
| **P1-8** | `stop-services.sh` / `start-services.sh` 会报告假成功 | macOS 脚本，无法在 Windows 验证 | 停机失败仍显示成功 |
| **P1-9** | 跨进程 WebSocket EventBus 仍是进程内实现 | 需要 Redis Pub/Sub 或事件 Outbox | Worker 事件不会推送到 UI |
| P2-1/2 | `ACCEPTANCE_REPORT.md` 仍为 V1.1 口径 | 本轮只更新了 README 的测试数量与状态 | 文档版本口径需统一 |
| P2-8 | Recovery Watchdog 与 API 启动可能并发触发 Recovery | 需要数据库级 advisory lock | 并发恢复可能互相覆盖 checkpoint |
